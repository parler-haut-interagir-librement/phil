# Moving a tenant

```sh
bin/console phil:tenancy:database:move retail tenant_retail      # to a database of its own
bin/console phil:tenancy:database:move retail shared             # back to the shared database
bin/console phil:tenancy:database:move retail tenant_retail --keep-source
```

A tenant moves from the shared database to one of its own, back, or between two dedicated databases. The target must
exist and be migrated beforehand: `phil:tenancy:database:create` creates and migrates the database of a tenant already
placed there, so a database that no tenant uses yet is prepared with the server's own tools and the application's
migrations. The placement service must implement `PlacementStore`, through which the move records the new placement:
`placement: dbal` gives one, on a table of the shared database ([Placements and suspensions in the
database](stores.md)). With the placements of `dedicated`, which the configuration fixes, the move is refused before
anything is copied.

## The steps

1. **The tenant is suspended.** Its requests are answered with a `503`, and its messages wait for the retry.
2. **Its rows are copied.** In one transaction on the target, any rows of the tenant left there by an earlier move are
   deleted, then every table of the tenant is copied, in the order of the copy plan. On PostgreSQL, the sequence of
   each generated key is moved up to the largest key, never back.
3. **The copy is verified.** Each table is read again, in the source and in the target, row by row in the order of its
   key, and the two are compared by a SHA-256 of every column of every row.
4. **The placement is recorded** in the `PlacementStore`.
5. **The source is emptied** of the tenant's rows, unless `--keep-source`. If that fails, the tenant is served from its
   target already: the rows left in the source are only unused, and a warning is logged.
6. **The tenant is resumed.**

Until the placement is recorded, any failure rolls the move back: the old placement is recorded again, the rows copied
to the target are deleted, and the tenant is resumed in its source, unchanged. The command prints why and ends with `1`.

The source and the target are read and written through two connections of their own, opened with the parameters of the
managed connection pinned to each database, in the tenant, and closed at the end.

## The copy plan

`CopyPlan` reads the tables of a tenant from the mapping of `entity_manager`:

1. the table of each root entity marked `#[TenantScoped]`, after the tenant-scoped tables its own table references,
   ties in the order of their names;
2. the table of each subclass of a joined hierarchy, after its parent's, reached through the root's key;
3. the join table of each many-to-many association that a tenant-scoped entity owns, reached through the owner's key.

Deleting goes the other way.

## Limits

- **Keys unique across databases.** A row keeps its key. A tenant moved into a database where another tenant already
  holds the same key — integer keys generated by each database — fails on the unique constraint, and the move is
  rolled back. Keys that are unique everywhere, such as UUIDs or ULIDs, move freely.
- **References between tenant-scoped tables must be acyclic.** Tables that reference each other cannot be ordered:
  the plan refuses them with `TenantNotCopyable`. A table that references itself is ordered by its key, which usually
  puts a parent first.
- **One column to reach a tenant.** A joined subclass or a join table is reached through a key of one column; a key of
  several columns is refused.
- **Only what the mapping knows.** Tables that are not tenant-scoped are not copied: each database holds its own
  reference data. A table outside the mapping, or a many-to-many association owned by an entity that is not
  tenant-scoped, is not copied either.
- **One server per move.** The source and the target are read with the platform of the shared connection.

## The cache, Messenger and the migrations

The cache of the tenant stays valid: it is scoped by the tenant's reference, and the data did not change. Messages that
waited during the move are handled, once the tenant is resumed, in its new database. The next run of
`phil:tenancy:database:migrate` migrates the database the tenant is in now.
