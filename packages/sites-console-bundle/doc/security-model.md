# Security model

## What is protected

- The sites: no request reaches an applier or a runner unless the console signed it for that site, now, once.
- The console's view of the sites: no answer is believed unless the site's key signed it for that request.
- The operators' actions: reading and acting take roles the identity provider gives; every action is journaled.

## Keys

Each side has an Ed25519 key pair, generated by `phil:sites-console:keys` with libsodium. The console keeps its
private key and the public key of each site; each site keeps its private key and the console's public key. Private
keys live in each application's environment or secrets and are never written, logged or shown by the bundle; a
`SigningKey` shows `***` when dumped.

The console stores no password, token or private key of any site: a public key verifies a site, it cannot act as one.
Leaking the console's database lets nobody call a site. Leaking the console's private key lets its holder send signed
requests to the sites until the key is rotated, as described below.

## Key rotation

The console key rotates without cutting any site off: during a rotation each agent accepts two console keys, the
current one and the next one. A request signed by either verifies; any other key is refused, and the date window, the
nonce and the site bound into the signature are checked as for every request.

The agent's accepted keys come from its configuration — `console_public_key` and, when set,
`console_next_public_key` — and from a store, written only by the `keys` action of the protocol. The store is a
cache pool, `key_pool` or else `cache_pool`, which must be shared by the site's servers and survive deploys: Redis or
a database, not a pool emptied by `cache:clear`. It holds public keys only, together with a fingerprint of the
configured keys it started from: once the configured keys change, they win over the store again, so that a deploy
always recovers a site.

`phil:sites-console:keys:rotate` runs the rotation from the console, in four steps:

1. It reads the next key, `console.next_private_key`. Without one, it prints a new pair to put there and stops: the
   private key never leaves the console's environment or secrets.
2. It stages the next public key on each site, one after the other, by a `keys` request signed with the current key.
   An agent stages a key only on a request signed with its current key.
3. Once every site holds the next key, the console signs with it. Which key signs is read from the rotation's row
   before each request, so every process of the console switches together.
4. It retires the previous key from each site by a `keys` request signed with the next key. An agent retires a key
   only on a request signed with the key that remains, and never retires its only key.

Each step on each site carries the same idempotency key on every attempt, `<rotation>:<stage|retire>:<site>`, so a
step delivered again is applied once and answers its first outcome. The run stops at the first site that fails and
prints the report per site; every step is journaled; running the command again resumes where it stopped. A site
removed from the console during a rotation is skipped. Nothing goes through a Messenger queue, and only public keys
leave the console.

When the rotation is finished, move `console.next_private_key` to `console.private_key` on the console, and set
`agent.console_public_key` to the new public key on each site at its next deploy. Until then, a site whose key store
is emptied falls back to its configured key, the previous one, and refuses the console: updating its configuration
recovers it.

### When a key leaks

- **The console's private key**: run a rotation at once. The holder of the leaked key can still send signed requests
  until each site has retired it, and can stage a key of its own on a site in the meantime. For a site that may have
  been reached, deploy its configuration with the new console key as `console_public_key`: a new configuration
  replaces whatever the store holds.
- **A site's private key**: its holder can answer the console as that site. Generate a new pair with
  `phil:sites-console:keys`, deploy it as the site's `private_key`, and register the new public key with
  `phil:sites-console:site:add`, which updates a known site.
- **The next private key, during a rotation**: start again with another next key. A rotation under way refuses
  another next key; once it is finished, run a new rotation to a fresh key.

## Requests

The console signs, with its private key:

```text
phil-sites-console/1 request
<site>
<action>
<date, Unix seconds>
<nonce>
<SHA-256 of the body, hex>
```

and sends the site, the date, the nonce and the signature in the headers `Phil-Console-Site`, `Phil-Console-Date`,
`Phil-Console-Nonce` and `Phil-Console-Signature`. The agent refuses the request, with `401` and a line in its logs,
when:

- a header is missing;
- the site is not its own `site_id`: a request for one site cannot be replayed to another;
- the date is more than `max_clock_skew` seconds — 300 by default — from its clock;
- the nonce is not 22 to 64 characters of base64url;
- the signature verifies with neither key of the console the site accepts, over this action and this body;
- the nonce was already accepted within twice the skew.

The nonce is remembered only after the signature verifies, so that nobody without the key can fill the store. The
store is the site's cache pool, and the check and the write of a nonce happen under a lock of `agent.lock_factory`:
two copies of one request arriving at the same time pass once, the other is a replay. On several servers, the pool
and the lock store must be ones they share. A nonce the pool does not save is never accepted: the request is answered
`503`, unsigned, and the console may send it again.

The body is read to one byte past 64 KiB and no further, before the signature is checked: a `Content-Length` above
the cap is refused unread, and a body longer than its header says is refused once the cap is passed.

## Responses

Every answer to a verified request is signed by the site over:

```text
phil-sites-console/1 response
<site>
<nonce of the request>
<status>
<SHA-256 of the body, hex>
```

in the header `Phil-Agent-Signature`. The console refuses an answer without it, signed by another key, or signed for
another request; a site answering for another site is refused too. It follows no redirect, stops after its time limit
and refuses an answer larger than 1 MiB. Every document it reads is checked member by member: sizes, depth, package
names, versions, states.

## Transport

Requests are signed, not encrypted. Agents are reached over `https` only, unless `allow_insecure_urls` is on for
development. The address of a site is read by `phil/url`, on a host name: an IP address is always refused, and
`localhost` unless that option is on. Only an operator can register a site, from the command line.

## Idempotency

A push carries its identifier, a step of a plan the plan and the site, and a step of a key rotation the rotation, the
operation and the site; the agent runs each once through
`phil/idempotency`, keyed by scope and identifier, with the SHA-256 of the body as its fingerprint. A retry gets the
first outcome; an identifier reused with another body is refused. The keys are kept seven days; a run in progress
holds its key fifteen minutes.

## Who may read and act

The screens take two roles of the user's token: the viewer role to read, the operator role to pull, deliver and run.
The bundle has no accounts of its own: the application's firewall authenticates the user against the identity
provider and maps its claims to roles. Every action is a POST with a CSRF token, and is journaled with the user
identifier. The commands are for the operators of the console's server; their `--actor` names them in the journal.

## Messages

The messages of the bundle — `PullSite`, `DeliverConfigurationPush`, `RunUpdatePlan` — carry identifiers only: a
site, a push, a plan, a number of batches, the user identifier of the operator. The settings stay in the database. A
key rotation runs from its command, without any message.

## What the bundle never does

- Deploy, host or provision a site, or run Composer on a server.
- Keep a credential of a site, or of its administrators.
- Push anything without a signature and a line in the journal.
- Follow a redirect, or call an address an operator did not register.

## Open points

- An external review of the protocol and of its implementation, required before a beta version.
